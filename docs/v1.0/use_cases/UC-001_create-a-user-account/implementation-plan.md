# UC-001 — Approved implementation plan

Approved by the user on 23 October 2026 for branch `v1.0_uc-001_create-a-user-account`.

## Scope and behavior

Open registration collects email, password, and password confirmation. Email is required, syntactically valid, and unique using ASP.NET Core Identity's normalized-email comparison, backed by a database uniqueness constraint. Passwords require at least 12 characters without uppercase, lowercase, digit, or symbol requirements. Password confirmation must match and is not persisted. Identity supplies password hashing and confirmation-token protection.

Registration creates a stable account identity with an unverified email. A confirmation link expires after 24 hours; successful confirmation verifies the email without signing the user in. First and last names belong to a later account profile page and are not registration inputs. Verified email remains a prerequisite for future financial/profile access.

This slice includes registration and email confirmation, Application orchestration and validation, Identity/EF Core SQL Server adapter code, account controller endpoints, and Blazor/MudBlazor screens. Development sends email to the local smtp4dev SMTP server; automated tests use a fake transport and synthetic accounts. Production uses the Azure Communication Services Email adapter. OpenIddict sign-in is a separate implementation slice. Account profile editing, recovery, account deletion, and budget profiles are outside this slice.

Provider decision amendments: On 27 October 2026, Azure Communication Services Email replaced the earlier Gmail selection for production verification and recovery email. On 29 October 2026, the user selected smtp4dev for local development and approved environment-specific provider selection. The smtp4dev and Azure adapters now implement the same Infrastructure transport boundary. The initial production configuration uses the Azure-managed sender domain and managed identity; Azure resources, role assignment, deployment configuration, cost/quota review, and a controlled live-send check remain deployment gates. Automated tests use fake transports and never send to real recipients.

## Acceptance criteria

- Valid registration persists exactly one account with a stable ID, a hashed password, and an initially unverified email, and makes a confirmation link available in smtp4dev during local development.
- Missing or malformed email, passwords shorter than 12 characters, and mismatched password confirmation produce validation feedback without creating an account. A valid 12-character password is accepted without requiring character classes.
- Repeated or concurrent registration with the same normalized email cannot create a second account. Email normalization does not introduce provider-specific dot or plus-address equivalence.
- A valid confirmation link verifies its intended account. Invalid, tampered, or expired links do not verify an account. Confirmation does not create an authenticated session or grant access to another account's data.
- The UI shows validation and recoverable failures, retains the email input, and does not report successful completion when the required operation failed. Passwords and confirmation tokens are excluded from logs and API error details.
- Development selects smtp4dev over local SMTP; Production selects Azure Communication Services Email and does not fall back to SMTP. If the environment's email settings are incomplete, account endpoints stay unavailable.
- User amendment on 23 October 2026 initially deferred database connections, migration application, and live database integration. On 26 October 2026, the user superseded that deferral for local development: integrate the UC-001 Identity store with localhost SQL Server LocalDB, apply migrations, and verify persistence and uniqueness locally. Azure SQL integration remains deferred. Automated email tests must never send messages to real recipients.

Confirmed follow-up decisions: duplicate registration receives the same generic acknowledgement as a successful request. Known email-delivery failures retain the unverified account, and resend is included. The acknowledgement must not promise that an account was created or an email delivered; it is also used for unknown/already-verified resend recipients and known delivery failures. The sender adapter records delivery failures without recipient/token payloads. Unexpected errors and cancellation propagate. Replaying a still-valid confirmation link is harmless success; invalid or expired tokens must still fail, even for an already-verified account. Provider adapters for smtp4dev in Development and Azure Communication Services Email in Production are included by the 29 October amendment. OpenIddict sign-in remains separate.
